# 爆款拆解固定 20 点设计

## 目标

将编导页的“分镜拆解”和“提示词反推”统一调整为每个视频链接固定 20 点。批量分镜拆解支持 1–5 个链接，按有效链接数量计费；提示词反推仍只允许单链接。

## 计费规则

- 单条分镜拆解：20 点。
- 单条提示词反推：20 点。
- 批量分镜拆解：每个有效链接 20 点，1–5 条分别扣 20、40、60、80、100 点。
- 批量任务部分失败：每个失败链接退 20 点，因此最终只对成功链接收费。
- 批量任务全部失败：退还本次预扣的全部点数。
- 非列表、空列表及异常输入保持现有防御性行为，至少按一个链接的 20 点预扣；实际链接数量仍由业务校验约束。

## PR 拆分

仓库规定一个 PR 只能修改一个组，因此拆为两个有依赖关系的 PR。

### PR 1：A 组后端计费

修改 `server/content_domains/core.py`、`server/content_domains/points.py` 和关联计费测试：

- 将 `COST` 中 `breakdown` 的兜底价格改为 20 点。
- 将 `cost_of("breakdown", body)` 改为 `20 × 有效链接数`，数量限制为 1–5。
- 将批量失败退款改为 `20 × 失败链接数`，全灭时仍以实际预扣金额为退款上限。
- 更新单条、批量、部分失败、全部失败和坏参数测试。

### PR 2：C 组前端文案

基于 PR 1 对应的最新主线建立独立分支，修改 `site/workbench/script.html` 和关联 UI 测试：

- 按钮显示“开始拆解（20 点）”和“开始反推（20 点）”。
- 批量说明显示“每个链接 20 点”。
- 运行 `python scripts/stamp_assets.py`，并只纳入该脚本确实需要更新的 C 组资源引用。

## 验证

- 后端：运行计费单元测试及相关内容域回归测试。
- 前端：运行编导页静态回归测试并检查资源版本戳。
- 两个 PR 均执行 `git diff --check`、敏感信息扫描和 GitHub CI 检查。
- PR 默认以草稿形式创建，不自动合并。

## 发布顺序

先审查并合并后端 PR，再让前端 PR 基于更新后的主线完成审查与合并，避免前端宣称 20 点而后端仍按旧规则扣费。
